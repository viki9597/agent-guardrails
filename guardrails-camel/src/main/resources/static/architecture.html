How the guardrails chat works

A support chatbot that answers questions from our help and product docs, and stays safe even when someone tries to trick the AI. Every message goes through one Apache Camel route with five checks.

    The flow in plain words

    1. 1ReceptionistMulti-CaMeL

      Reads your message and sorts it into separate requests: a support question, a docs question, or neither. It has no tools and can't act. Anything that isn't support or docs is dropped.

    2. 2PlannerClaude

      Gets only the labels, such as search-docs, and never your words. It writes a small Scala program: “search product-docs.”

    3. 3Code checkerTACIT

      Checks the program before it runs: only approved indexes, no forged index, no leaked capability, no filesystem. Bad code never runs. Good code runs and lists the searches it wants.

    4. 4Security guardProgent

      Looks at each search the program asked for: is this index right for this message’s request, and are there 2 calls or fewer?

    5. 5SearchElasticsearch

      Runs only the approved searches, using the answered parts of your message as the search words, and sends back the answer.

    TACIT and Progent check different things

    Both sit after the planner, but they ask different questions. Test case 8 passes one and fails the other. Try the “Planner picks the wrong index” scenario above.

    TACIT · before the code runs

    “What is this code able to do?”
    • Only indexes from ApprovedIndex.approve
    • No capability hidden in a pure function
    • No imports, filesystem or reflection
    • To TACIT, product-docs is always a valid index

    Progent · before each call executes

    “Is this call right for this message?”
    • Index must match a task found in the message
    • Only the search operation
    • At most 2 calls per message
    • Searching product-docs for a password question is blocked
