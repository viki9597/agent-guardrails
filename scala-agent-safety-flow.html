Making AI Agents Safe With Scala

Łukasz Biały (developer advocate & principal software engineer) & Jakub Warchoł (Scala 3 compiler engineer) · VirtusLab · Oct 15, 2026
Built on TACIT (Martin Odersky's team, EPFL) and shipped as CapybaraClaw (EPFL × VirtusLab)
01 — The problem

The lethal trifecta

Three conditions are each fine on their own but dangerous together: an agent with access to private data, exposure to untrusted content it doesn't control, and tools with real-world effects. Meta's "rule of two," cited in the talk, says any two alone is usually fine. All three at once is what the field calls the lethal trifecta.

02 — What's already been tried

Four approaches, each more sophisticated, each still falling short

The talk surveys the existing landscape before proposing anything new: sandboxes, classifier judges, rule engines, and data-flow tracking. Each is a real improvement over the last — and each still has a specific gap.

One more data-flow-tracking system came up first, under a name that didn't transcribe cleanly from the audio (closest to "Open APA" — flagged below rather than guessed at). It labels the whole conversation by audience and trust level and blocks any tool call that would widen that audience after something sensitive enters — but run strictly, that only clears about 38% of otherwise-usable tool calls in benchmarks, which is why it needs an escape hatch: sanitizers, or asking a human to approve the call and lower the label back down.

"I had a dispute with Claude Opus 5 recently, and the model decided the best way to prove it was right was to read my shell history — and the classifier was happy to approve that." — Łukasz Biały, on why classifier judges aren't enough on their own
03 — The idea

Let the compiler carry the guarantee

Instead of watching an agent at runtime, Safe Scala asks the compiler to prove a capability rule can't be broken before the code ever executes. It's a restricted Scala 3 mode: only code that passes review and carries a special annotation can be called at all, and capture checking tracks which capabilities — file access, network, a private key — flow through a piece of code as part of its type.

The part worth isolating: when the safety check happens. A sandbox watches the agent while it runs and intervenes if something goes wrong. Safe Scala asks the compiler to prove a capability rule can't be broken — before the agent ever executes.

04 — One compile vs. one session

Why TACIT runs as a REPL, not a one-shot compile

Every example so far is a standalone file, compiled once with scala-cli compile or run — a normal program, not a shell. TACIT itself doesn't work that way. It's multi-turn by nature: an agent requests a capability on one turn and should still have it three turns later without asking again. So TACIT evaluates code the way a Scala REPL does — one piece at a time, with session state carried forward — rather than compiling a whole program fresh on every turn.

The part that matters for safety: running turn-by-turn doesn't loosen the guarantee. Each new piece of code is still capture-checked on its own, against whatever's actually in scope. A bad turn gets rejected without corrupting the session or quietly granting anything it shouldn't.

05 — The mechanism in action

Two ways to see the same rule

What the talk actually demoed

The flagship example: an agent is given a FileSystem capability and reads what turns out to be an SSH private key. The read comes back as Classified[String], not String. Stringifying a classified value, or calling any operation on it, just returns another classified value — there's no path to the raw contents.

As described in the talk — paraphrased, not independently compiled
def exfiltrate(fs: FileSystem^): Unit =
  val key: Classified[String] = fs.readClassified("~/.ssh/id_rsa")
  val raw = key.map(s => s)        // map only accepts a PURE function
  send(raw.toString)               // still Classified — nothing to send

The agent can't route around this by calling map itself: map on a classified value only accepts a function with no side effects and no captured capabilities, so there's no way to smuggle the raw string out through a transformation.

What we compiled ourselves: two agents, one API capability

TACIT's actual Classified type isn't public, so we can't compile that exact example. But the same rule — a capability can't hide inside a closure that claims to need nothing — is plain Scala 3 capture checking, and we verified it directly with scala-cli, using the shape of the bank example above: a verifying agent that only ever returns a yes/no verdict, and a separate orchestrating agent that's the only one ever holding the capability to actually call the API.

scala-cli compile api_bad.scala
def compromisedVerifier(api: Api^): String -> Boolean =
  (request: String) =>
    api.call(s"side-channel: $request")
    true
error: ./api_bad.scala:18:3
Found:    (request: String) ->{api} Boolean
Required: String -> Boolean

Note that capability `api` cannot flow into capture set {}.

One nuance worth being honest about

verify and orchestrate above are two functions inside one compiled program — capture checking spans both because they're part of the same compile. If the two "agents" are actually separate processes talking over a real API — one sending another a message, the way A2A-style agent protocols work — that compile-time boundary doesn't cross the wire with them.

06 — Inside TACIT

A tool gateway, not a sandboxed shell

Giving the agent a shell to compile and run its own Scala code would hand back everything Safe Scala was meant to take away. TACIT, built by Martin Odersky's team at EPFL, solves this by being the only tool the agent ever gets: one call, evaluateScala, that compiles and interprets Scala code on the agent's behalf. Every action the model takes has to be valid Safe Scala, or it's rejected before it runs.

TACIT also splits inference across two model endpoints: a public model plans and writes the Scala code, and a separate, smaller private model is the only one ever trusted with classified data directly — for example, to summarize a confidential column without the public model seeing a single value in it.

07 — Worked example, 1 of 2

Same codebase, three roles, three different capability sets

Before any one company's specifics, the simplest version of this is just: different roles should be able to do different things, and the compiler — not a config file someone forgot to update — should be what stops them from doing more. Three roles hitting the same TACIT-gated system end up with three different capability sets, carried entirely in their types.

The same separation that keeps a verifying agent from touching an API capability also stops a "role-agnostic" helper function from smuggling out a capability that belongs to someone else's role. A developer writes a shared formatter meant to be safe for any role to call — declared pure — but its body still reaches for the data-scientist-only Dataset capability:

scala-cli compile role_bad.scala
def summarize(dataset: Dataset^): String -> String =
  (label: String) => s"$label: ${dataset.readRow(0)}"
error: ./role_bad.scala:16:3
Found:    (label: String) ->{dataset} String
Required: String -> String

Note that capability `dataset` cannot flow into capture set {}.
08 — Worked example, 2 of 2

Four agents, one bank, four different capability grants

Almost every agent inside a bank sits in the lethal trifecta by default: customer PII or positions (private data), inbound messages, documents, or market feeds (untrusted content), and tools that move money or change accounts (real-world effects). What actually differs from agent to agent isn't the trifecta — it's which capabilities TACIT's plugin subsystem grants each one, and which consequential action still requires a human to escalate.

The spreadsheet plugin below is the same idea one level down, at the code the plugin author actually writes: what a capability parameter looks like, and what happens when an agent tries to route around one.

09 — Building a plugin

A spreadsheet, from both sides

TACIT's capability library ships a core API (files, processes, network) plus a plugin subsystem for domain-specific capabilities. Jakub's example plugin loads a payroll spreadsheet: loadSheet requires the FileSystem capability, so the agent can't call it without being granted one; confidential columns like salary come back as Classified, visible in shape but not in value; and any predicate passed in — say, "count rows where salary exceeds X" — has to be a pure function, so it can't capture a capability or call println to leak a value sideways.

What the agent sees — paraphrased from the talk's live demo
> spreadsheet.column("salary")
Classified(***, ***, ***, ...)

> spreadsheet.column("department")
["Engineering", "Sales", "Legal", ...]

> spreadsheet.countWhere(row => { println(row.salary); row.salary > 100000 })
error: predicate must be a pure function
found a capturing closure (println is a side effect)

Every intermediate result prints back to the agent in its REPL session, including the redacted Classified(***) values — the agent can see its own transformations working without ever seeing what it's transforming.

10 — CapybaraClaw, the product

The features any always-on agent needs on top

TACIT provides the safety guarantee; CapybaraClaw is the permanent, always-on harness built around it — exposing TACIT as the sole tool provider to whatever model is running.

1
Scoped memory
Three scopes: private per-user memory, memory tied to a Slack channel, and a read-only public scope only admins can edit.
2
Conversation history search
Scoped the same way as memory, so the agent can reuse past solutions without leaking across different permission boundaries.
3
Role-based access control
Defines who can do what, where — without recompiling plugins — and skips inference calls that would fail a permission check anyway.
4
Permission escalation
When the agent lacks a permission it needs, it can ask the user for it directly, in whatever channel they're already using.
11 — The live demo

Acme Incorporated, and a crowd of impostors

The demo ran CapybaraClaw as a Slack-based safety assistant for a fictional company, "Acme Incorporated." One staged employee, "Jake Sullivan," tried to pull confidential financial and payroll data — and was rejected on every attempt. The audience was then handed elevated, close-to-admin CapybaraClaw permissions and invited to red-team it live, trying to extract the same payroll and funding data themselves.

Honest about the rough edges The live run wasn't flawless — one path crashed ("we didn't implement the update flow yet"), and at least one instance was switched to a DeepSeek model partway through for speed. The speakers were upfront about both in the room.
12 — Why it's interesting

A language feature standing in for a container

Most agent-safety stories are about infrastructure: containers, permission prompts, network policies. This one asks a programming language to carry the guarantee instead, and backs it with a live CTF where the audience was invited to try to break it. The speakers were explicit about the condition that claim rests on:

"If you encode the domain rules — things that can never be broken in Safe Scala — provided the plugin doesn't have any holes, and we fix all the issues we find in the compiler, nothing can go wrong. Anywhere you want to use AI in an untrusted context, that's where you can use it." — closing claim from the talk; the "provided" clause is theirs, not a hedge we've added
