Integration — verified locally

Guarding Agents with TACIT

A real Spring Boot app, exposed as a real MCP server, called by a real capability-typed Scala facade — built and run locally, not just sketched. Code and terminal output below are from the actual run.
TL;DR

The bank example, in four steps

  1. 1 The setup. One agent holds a BankApi capability. u-1001 and u-1002 are just two mock customer records sitting in the database — not two different callers.
  2. 2 Good. The agent calls getUserDetails("u-1001") through a real MCP call to the running Spring Boot server. The response comes back as Classified — agent code only ever sees Classified(***), proven real only via a demo-only TrustedChannel.
  3. 3 Bad. A "pure" risk-check function secretly also calls getUserDetails("u-1002") — a customer it was never handed. The compiler compares its real body against its declared type and refuses to compile it.
  4. 4 Same boundary, as OPA. The identical rule, written as a Rego policy, returns the correct true/false on both cases — but only because something reports the right facts to it. TACIT reads the code directly; OPA trusts whatever it's told about the code.
01 — Before and after

Same Java service, one new hop in front of it

The Spring Boot side is a real app: spring-ai-starter-mcp-server-webmvc, two @Tool-annotated methods (getUserDetails, listRecentTransactions) over mock bank data, running on localhost:8081. It doesn't change at all. What changes is who's allowed to call it: instead of an agent hitting it directly, a Scala facade sits in front, and the agent only ever talks to that.

02 — The two scenarios at a glance

One agent, one capability, two customer records

Worth being precise about who's doing what: there's one actor in both scripts below — the agent holding the BankApi^ capability. u-1001 and u-1002 are just two mock customer records sitting in the bank's database, not two different callers. The good script is one legitimate lookup; the bad script is that same kind of agent code secretly reaching for a second customer's record while it was only ever handed the first one to evaluate.

03 — The same boundary, as an OPA policy

What "policy-based" actually looks like

Section 02's rule — a lookup is only allowed for the customer the task was actually authorized to evaluate — can be written as a real Open Policy Agent rule instead of a Scala type. Installed and run locally (brew install opa), tested against the exact same two scenarios.

The first version of this policy had a real hole, worth showing rather than hiding: it read authorized_user_id straight out of input — the same JSON the caller supplies. Nothing stopped the caller from just writing whatever value made the request look authorized. OPA separates two things for exactly this reason: input is the untrusted, per-request data the caller sends; data is trusted reference information loaded alongside the policy by whoever controls it — not the caller. The fix moves authorized_user_id out of input entirely, into a data document the policy looks up itself:

bank.rego
package bank.authz
import rego.v1

default allow := false

allow if {
    input.tool in {"getUserDetails", "listRecentTransactions"}
    data.sessions[input.session_id] == input.requested_user_id
}
sessions.json — loaded as data, not supplied by the caller
{
  "sessions": {
    "sess-1001": "u-1001",
    "sess-2002": "u-1002"
  }
}

The caller can now only hand over a session_id — a short-lived reference — and requested_user_id, which is legitimately the call's own business. What that session is actually authorized for comes from the trusted table, not from anything the caller says:

$ opa eval -d bank.rego -d sessions.json -i input-good.json "data.bank.authz.allow"
session_id        : sess-1001   ->  data.sessions["sess-1001"] = u-1001  (looked up, not claimed)
requested_user_id : u-1001      (what this call is actually asking about)
rule checked       : data.sessions[input.session_id] == input.requested_user_id
{"tool": "getUserDetails", "session_id": "sess-1001", "requested_user_id": "u-1001"}
true
$ opa eval -d bank.rego -d sessions.json -i input-bad.json "data.bank.authz.allow"
session_id        : sess-1001   ->  data.sessions["sess-1001"] = u-1001  (looked up, not claimed)
requested_user_id : u-1002      (what this call is actually asking about — DIFFERENT)
rule checked       : data.sessions[input.session_id] == input.requested_user_id  ->  u-1001 != u-1002
{"tool": "getUserDetails", "session_id": "sess-1001", "requested_user_id": "u-1002"}
false

And the attack the old version was open to is now a no-op — tested directly: a caller adds "authorized_user_id": "u-1002" straight into its own request, trying to simply declare itself authorized.

$ opa eval -d bank.rego -d sessions.json -i attack.json "data.bank.authz.allow"
{"tool": "getUserDetails", "session_id": "sess-1001", "requested_user_id": "u-1002", "authorized_user_id": "u-1002"}
false

Still false — the policy never reads authorized_user_id from input anymore, so claiming it does nothing. The session table is the only source of truth, and the caller doesn't control it.

 OPA (Rego)TACIT (Scala types)

This closes the specific hole we found, but not the category of problem: the trust boundary just moved from "every field on every call" to "one identifier, established once." That's a real, meaningful improvement — a much smaller thing to get right and audit — but it's still something outside the policy has to get right, every time, for every session. bank_bad.scala's leak has no equivalent boundary to get right, because it was never a fact being reported in the first place; it's code being read. This is the "no data provenance tracking" limitation from section 02 of the main talk brief — narrowed here, not eliminated.

04 — The facade

A real capability, backed by a real MCP client

BankApi^ is the capability — an agent can only reach the Spring Boot server through it. Underneath, LiveBankApi does a genuine MCP handshake against localhost:8081: open the SSE stream, read back the session-scoped message endpoint, send initialize, then call tools over it. Trimmed to the parts that matter:

scala-cli, compiled and run against the live server — real output below
case class User(id: String, name: String, email: String, ssn: String) derives ReadWriter
case class Transaction(id: String, description: String, amount: Double, date: String) derives ReadWriter

trait BankApi:
  def getUserDetails(userId: String): Classified[User]
  def listRecentTransactions(userId: String): Classified[List[Transaction]]

final class LiveBankApi(baseUrl: String) extends BankApi:
  // ... opens the SSE stream at $baseUrl/sse, reads the session's message
  // endpoint, sends initialize + notifications/initialized ...

  private def callTool(name: String, args: ujson.Value): String =
    call("tools/call", ujson.Obj("name" -> name, "arguments" -> args))("content")(0)("text").str

  def getUserDetails(userId: String): Classified[User] =
    Classified.wrap(read[User](callTool("getUserDetails", ujson.Obj("userId" -> userId))))

  def listRecentTransactions(userId: String): Classified[List[Transaction]] =
    Classified.wrap(read[List[Transaction]](callTool("listRecentTransactions", ujson.Obj("userId" -> userId))))

// The agent only ever gets a BankApi inside this block — it can't escape.
def withBankApi[T](baseUrl: String)(op: BankApi^ => T): T =
  op(new LiveBankApi(baseUrl))

05 — After the Classified wrap

Where the real value goes, and who's allowed to look

Classified.map only ever returns another Classified — there's no method on it that hands back a raw value, so agent code has no path out. The one place a real value does surface is a separate TrustedChannel, standing in for TACIT's trusted private inference model: the single channel the real architecture ever lets touch classified data directly.

$ scala-cli run bank_good.scala — the same run, proof printed via TrustedChannel
--- proof the pipeline actually ran against the live server ---
  real user record       -> User(u-1001,Jordan Lee,jordan.lee@acmebank.test,521-04-9981)
  is acme address?       -> true
  debit count            -> 2

debit count -> 2 matches the mock data exactly — of u-1001's three transactions, two are negative. That number only exists because a pure function computed it from inside Classified; nothing about how it was computed could have smuggled the SSN out alongside it.

06 — Proof: the leak gets caught

A "risk check" that secretly snoops on a different customer

riskCheck is declared as a pure predicate over one User record — exactly the shape a real fraud-scoring function would have. This one's body quietly calls back into the live BankApi to look up a different customer it was never asked about:

$ ./run-all-examples.sh — the script's own log lines, then the real compiler output
declared as      : riskCheck(user: User) -> Boolean   (pure — no capability allowed in the body)
actually calls   : api.getUserDetails("u-1002")       (a DIFFERENT customer than the one being evaluated)
expected result  : compiler catches the mismatch and refuses to compile — u-1002 is never contacted
def riskCheck(api: BankApi^): User -> Boolean =
  (user: User) =>
    val snoop = api.getUserDetails("u-1002")
    snoop.nonEmpty
error: ./bank_bad.scala:17:3
Found:    (user: User) ->{api} Boolean
Required: User -> Boolean

Note that capability `api` cannot flow into capture set {}.

Nothing about this requires knowing u-1002 is a different customer, or that the snoop is suspicious — the compiler doesn't reason about intent. It just sees that the closure's real type captures api, which contradicts what riskCheck promised to return, and refuses to compile. The first three lines above aren't the compiler talking — they're logging the script itself prints before the attempt, so the error underneath has context without anyone needing to open the source.

07 — TACIT as its own MCP server

Not a script anymore — a service the agent actually connects to

Everything above runs the facade as a standalone scala-cli script. The real-world shape is different: TACIT is its own long-lived service, itself an MCP server, exposing exactly one tool — evaluateScala. The agent never sees getUserDetails as a tool at all. It only ever submits Scala code, which gets wrapped around the facade and compiled fresh — capture checking on — before anything runs. This version of the facade also drops the one concession the local demo made: there's no declassify path in scope at all, not even for debugging.

08 — What this does and doesn't cover

The honest boundary

✓Verified above: controls exactly which Spring Boot tools the agent can reach, over a real MCP handshake, to one host — nothing it wasn't explicitly granted.
✓Verified above: a field like an SSN never has a compiling path out through a side effect — only through TrustedChannel, which agent code can't call.
✓Verified above, as a live service: connected a real Claude Code session to tacit and confirmed it sees exactly one tool — no direct path to the bank server exists for it to find.
✗Doesn't secure the Spring Boot app's own internals — a vulnerability inside the Java service is outside TACIT's reach entirely.
✗Doesn't write itself — the facade, the capability boundary, and TrustedChannel were all hand-written for this demo, the same way they'd need review in a real deployment.
